### 1.3 실현된 가치

| 관점 | 내용 |
|------|------|
| **Problem** | `.optional()`/`.nullable()` 결함이 3번째로 재발했다(2차 `closedOn` → 4차가 닫음 → 3차 `cycles.name`/`yearMonth`). 3차가 PDCA 절차 없이 구현해서 2차의 회고 학습이 다시 읽히지 않았고, cycles 도메인 런타임 실증은 0건이라 이 재발이 코드 정독으로만 발견됐다 |
| **Solution** | `name`·`yearMonth`를 nullable로 넓히고 엄격 pair 술어(null=해제·undefined=무변경 구분)를 create·update 양쪽에 걸어 C-1과 I-1을 한 형태로 닫았다. `CycleForm`은 해제 시 `null`을 보내고 형이 지정한 문안으로 confirm을 띄운다. cycles L1 하네스(15 시나리오)를 red(6건 실패)→green(15/15) 순서로 실증하고, 이번엔 저장소에 커밋해 자산으로 남겼다 |
| **Function/UX Effect** | 형이 버전 카드에서 `☐ PDCA 사이클 연결` 체크를 끄고 저장하면 confirm 문구("문서 버튼이 사라지고, 사이클명 'X'를 다른 버전이 쓸 수 있게 됩니다. (문서 자체는 삭제되지 않음)")를 거쳐 실제로 해제된다(전에는 에러 없이 저장되고 그대로 남았다). `PATCH /api/cycles/:id`에 편측 필드만 보내면 200이 아니라 400이 온다 |
| **Core Value** | **"같은 결함이 세 번 나면 그건 코드 문제가 아니라 절차 문제다."** 이 사이클은 결함 3건을 닫는 동시에, 3차 회고 Try P-1(직전 Try 이행 현황 표)·P-2(zod "지울 수 있는가" 열)·P-3(L1 시나리오 DoD 체크박스)의 **최초 적용 사례**가 됐다 — 세 형식 전부 이 사이클 문서에서 실제로 결함을 잡는 데 쓰였다(§5.2) |

## 6. 회고

### 6.1 잘된 것 (Keep)

- **P-1~P-3 형식을 문서에 형식으로 적용한 것이 실제로 결함을 잡았다.** P-2(zod "지울 수 있는가"
  열, Design §3.3)가 `releaseNote`는 `''`로 남기고 `name`/`yearMonth`만 `null`로 가야 한다는
  판단을 4필드 전부에 강제했고, P-3(L1 시나리오 DoD 체크박스, Plan §4.1)이 "작성"이 아니라
  "실행"을 기준으로 못박아서 하네스를 실제로 두 번(red·green) 돌리게 만들었다. 형식이 권고로만
  남았던 3차와 달리, 이번엔 형식이 판정 기준 그 자체였다.
- **red 먼저, 수정은 그다음(module 순서 반전)이 하네스의 가치를 실측으로 증명했다.** 4차와
  반대로 검증→코드 순서를 잡은 결과, module-1에서 하네스 자체 결함 2건(공유 픽스처 오염·잘못된
  타겟)을 **수정 코드를 쓰기 전에** 발견했다. 순서를 지키지 않았다면 이 결함들이 green 결과에
  묻혀 안 보였을 것이다.
- **Design의 예측을 실행으로 검증하고, 틀린 부분을 숨기지 않고 기록했다.** red 예측 5건 vs
  실측 6건의 차이(`n4`의 `#10` 종속)를 "Design이 맞았다"로 얼버무리지 않고 analysis §2.2에
  정확히 왜 틀렸는지 적었다 — 이게 바로 3차가 놓친 "실행해야 보이는 것"의 실물 사례다.
- **형이 Plan v0.1의 하네스 자산화 권고를 반론으로 뒤집은 것이 옳았다.** "F34 자체가 삭제
  선례의 비용 증명서"라는 지적이 정확했고, 절충안(커밋+분리 실행+skip 가드)이 실측 3축 전부
  성립해 무리 없이 채택됐다. 클로드의 최초 권고가 항상 맞는 게 아니라는 걸 이 사이클이
  보여준다.

### 6.2 개선이 필요한 것 (Problem)

- **Design 문서가 시나리오 간 상호작용(공유 픽스처를 통한 부작용)을 지면 검토만으로는 못
  잡는다는 게 또 확인됐다.** V1~V5로 5건이나 사전 실측했는데도, 정작 하네스 시나리오 15개
  사이의 상호작용(한 시나리오의 mutation이 다른 시나리오의 전제를 깨는 것)은 실행 전엔 안
  보였다. 사전 검증이 아무리 꼼꼼해도 "여러 시나리오를 한 파일에서 순서대로 돌린다"는 조건
  자체가 만드는 리스크는 실행으로만 잡힌다.
- **`git tag`·릴리즈 프로세스가 PDCA 사이클 종료 절차와 아직 안 맞물려 있다.** RULE.md 종료
  절차 4번이 "이번 사이클 태그"를 전제하는데, 정작 태그를 언제·누가·어떤 기준으로 만드는지는
  문서화돼 있지 않다. 이번에도 §4.2에 확인 필요 항목으로 미뤘다 — 3차가 만든 `cycles.version`
  기능과 git tag의 관계 정리(P-5)가 여전히 안 됐다는 증거다.

### 6.3 다음에 시도할 것 (Try)

1. **[다음 Plan §1.4 필수 항목] 이 사이클의 하네스(`server/cycles.l1.ts`)를 다음 사이클이
   재사용했는지 확인한다.** 재건축했다면 RK-27이 실현된 것 — D-35(커밋 자산화) 판단 자체를
   재검토해야 한다. 재사용(확장)했다면 P-1~P-3처럼 "형식이 값을 한 사례"로 report Keep에
   추가한다.
2. **L1 하네스를 설계할 때 "시나리오 간 상호작용 매트릭스"를 Design 단계에 명시적으로
   포함한다.** 이번엔 실행 후에야 `#5`가 `#4`의 레코드를 오염시키는 걸 발견했다 — "이 시나리오가
   쓰는 레코드를 다른 어느 시나리오가 같이 쓰는가"를 표로 만들면 module-1 최초 실행 전에 잡을
   수 있었을 것이다.
3. **git tag·릴리즈 시점을 RULE.md 종료 절차에 명시한다(P-5 연장).** "이번 사이클 태그"가
   언제 생기는지 규칙에 없어서 매 사이클 임기응변으로 처리되고 있다. cycles 기능(3차 산출물)과
   실제 git tag 운영을 한 원천으로 묶는 결정이 필요하다.
4. **P-1~P-3 형식이 두 사이클 연속(4차·이번) 값을 했으니, RULE.md·템플릿 정식 개정을
   검토한다.** 이번 사이클이 "형식 적용까지만" 스코프를 잡은 이유가 "형식이 실제로 값을 하는지
   확인한 뒤 승격"이었는데, 이번 report가 그 확인이다 — 다음은 승격 여부를 형이 판단할
