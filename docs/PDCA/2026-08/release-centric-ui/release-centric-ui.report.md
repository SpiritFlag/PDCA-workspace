### 1.3 실현된 가치

| 관점 | 내용 |
|------|------|
| **Problem** | 3차(cycle-release-note)가 버전을 DB의 1급 엔티티로 세웠지만 UI는 URL도 없는 접힌 행이었고, PDCA 문서가 릴리즈 카드·사이드바·문서 목록 3중 노출되며 동일 라벨 도배(CRN I-5)와 일반 문서 매몰을 동시에 일으켰다 |
| **Solution** | 릴리즈 상세 페이지(`/r/:version`) 신설로 버전=URL을 만들고, 그 페이지를 PDCA 4문서 진입점+릴리즈노트로 삼았다. 사이드바·문서 목록에서 `kind='pdca'`를 걷어내고, 삭제는 릴리즈·문서 둘 다 목록이 아니라 상세 페이지 하단으로 이관했다(S6·S10) |
| **Function/UX Effect** | 사이드바 버전 클릭이 상세로 착지, 문서 트리·목록에 일반 문서만 남음, projectId를 DB 조회 없이 화면에서 복사 가능. 코드 구현은 완결됐으나 **화면상 실제 동작은 형이 아직 개별 확인하지 않았다**(§1.4) |
| **Core Value** | "PDCA 산출물의 단위는 문서가 아니라 릴리즈다"(3차 D-19)를 데이터 모델에 이어 **UI 정보구조까지 관철**했다 — 코드 수준에서는. 이 사이클 자체의 핵심 교훈은 기능이 아니라 **판정 방법론**이다: 완결과 실증을 섞지 않고 정직하게 분리했다(§6) |

## 6. 회고

### 6.1 잘된 것 (Keep)

- **판정 원칙을 미리 선언하고 압력 속에서도 그대로 지켰다.** Plan §4가 "브라우저 실증
  없는 항목은 Met 아님"을 사전에 못박았고, 형이 실제로 라이트 패스를 택했을 때(귀찮음
  표명) 그 선언을 흔들지 않고 8/9 Partial로 정직하게 기록했다. **97%(정적)와 11%(SC)를
  섞지 않은 것**이 이 사이클에서 가장 값진 결정이다 — 편해지려면 얼마든지 "대충 다 Met"으로
  적을 수 있었다.
- **7T-3(gap-detector 재확인 루틴)이 실제 결함을 잡았다.** G-1(`!` 단언)은 gap-detector
  혼자로는 "형태만 있고 안전한지 불확실"에 그쳤을 텐데, 직접 code Read + `tsc -b` 실행이
  TS의 실제 동작(프로퍼티 접근은 클로저 경계를 넘으며 내로잉이 끊긴다)을 실증하고 올바른
  수정 패턴을 확정시켰다.
- **Do 단계 무회귀 검증이 Check의 C43 근거로 그대로 재사용됐다.** gap-detector가 Bash
  미보유로 CLI를 못 돌리는 구조적 한계를, Claude가 직접 실행해서 메운 패턴이 8차에 이어
  두 번째로 반복됐다 — 이제 이건 우연이 아니라 **이 프로젝트의 표준 절차**로 봐야 한다.
- **실측 우선 원칙(Plan §3.1)이 설계 단계 함정을 사전에 막았다.** RK-48(pdca 필터가
  `existingPaths`를 오염시키면 4버튼이 붕괴)을 Plan 단계에서 미리 지목하고 Design·Do·Check
  세 단계 모두에서 반복 확인했다 — 실제로 코드에서 위반 0건.

### 6.2 개선이 필요한 것 (Problem)

- **"브라우저 실증"이 사이클 하나에서 8/9 항목의 유일 병목이 됐다.** 이 프로젝트가 개인
  앱이라 QA 인력이 없고, Playwright 같은 자동화도 의도적으로 안 들였다(Design §8.1) —
  구조적으로 **형의 수동 확인이 유일한 런타임 검증 수단**인데, 이번처럼 형이 피로하면
  검증 자체가 통째로 비게 된다. 3차(cycle-release-note)가 겪은 것과 동일한 구조적 취약점이
  이번에 다시 노출됐다 — 그때는 사전 경고가 없어 사후 발견이었고, 이번엔 사전 경고 후에도
  같은 결과가 났다는 점이 다르다.
- **Success Criteria 9건 중 8건이 브라우저 의존이라는 사실 자체를 Plan 단계에서 더 일찍
  문제 삼지 않았다.** Plan §6.3에서 검증 환경 존재는 확인했지만("모바일 확인 가능?"),
  "이 사이클의 SC 대부분이 형 1인의 수동 확인에 의존한다"는 구조적 리스크는 명시적으로
  기록하지 않았다.

### 6.3 다음에 시도할 것 (Try)

1. **[신규 제안] SC를 Plan 단계에서 "코드로 검증 가능"과 "브라우저만 검증 가능"으로
   미리 분류하고, 후자의 비율이 높으면(예: 70% 이상) Plan Checkpoint에서 형에게
   "이 사이클은 실증 부담이 크다"고 사전 경고한다.** 이번처럼 사이클이 끝난 뒤에야
   "8/9이 브라우저 의존이었다"는 걸 발견하면 이미 늦다.
2. **최소 침습 스모크 테스트를 Do 단계에 추가하는 걸 검토한다.** Playwright 전면 도입은
   과하지만(Design D-15 판단 유효), "핵심 페이지가 500 에러 없이 렌더되는지"·"라우트가
   정확한 컴포넌트로 매칭되는지" 정도의 최소 curl/fetch 기반 체크는 Bash로도 가능했다 —
   실제로 이번 Do 단계에서 `curl`로 web:200/api:401 스모크 체크를 했는데, 이걸 정식
   테스트 스텝으로 승격하면 "코드가 안 죽는다"는 최소 신뢰는 형의 손을 안 빌리고도 확보된다.
3. **다음 사이클이 이번 8건의 Partial을 실제로 Met으로 전환했는지 회신받는다.** 형이
   dev 서버(localhost:5173)를 통해 아무 때나 확인할 수 있으므로, 다음 Plan §1.4(P-1 표)에
   "release-centric-ui의 E1~E10을 실제로 확인했는지" 항목을 필수로 넣는다.
