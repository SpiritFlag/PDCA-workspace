## 6. 회고

### 6.1 잘된 것 (Keep)

- **사람 실증이 정적분석·L1 하네스로는 원천적으로 못 잡는 결함을 잡았다.** D-98(`projectName`
  누락)은 코드가 문법적으로 완결돼 있고 테스트가 전부 그린이어도 드러나지 않는 종류의
  결함이다 — "이 계정에 프로젝트가 여러 개 있다"는 실사용 조건 자체가 Plan §3.1 실측
  단계에 없었다. gap-detector·L1 37건 전부 그린인 상태에서도 실사용 모순이 있을 수
  있다는 걸 이번 사이클이 실증으로 보여줬다.
- **결함을 발견 즉시, 승인 절차를 지키며 고쳤다.** RULE.md "요구사항이 기존 코드 구조와
  충돌하면 구현 전에 질문한다"에 따라 형에게 먼저 확인받고(AskUserQuestion) 인자 설계를
  바꿨고, 커밋·push(프로덕션 재배포)도 매번 명시적으로 확인받았다. 비가역 작업(배포 2회)
  전부 사전 승인을 거쳤다.
- **9T-1(SC 검증 수단 열)의 사전 산정이 실제로 맞았다.** 사람 의존 비율 28.6%로 산정하고
  경고 임계(70%) 미만이라 사전 경고를 안 했는데, 실제로 사람 실증 2건이 문제없이(오히려
  결함을 잡으며) 완료됐다 — 9차(88.9%, 8/9 Partial로 마감)와 뚜렷이 대비된다.
- **6T-1(l1-harness 재사용) 채점이 이번에 성립하고 통과했다.** `getPrompt`가 기존 `rpc`를
  무수정 호출해 재건축 없는 확장을 실증했다 — 6차 D-48이 의도한 형태 그대로.
- **RK-56의 비관적 예측이 실측으로 뒤집혔다.** 웹 커넥터의 prompts 지원 여부가 공식
  문서에 없어 미지원을 걱정했는데 실제로는 지원했다 — 클라이언트 동작은 실측 전엔
  모른다(6차 교훈)가 이번엔 좋은 방향으로 재확인됐다.

### 6.2 개선이 필요한 것 (Problem)

- **사이클 중간 사후 결정(D-98)의 문서 반영이 절 단위로 누락됐다.** D-98이 나온 시점에
  §4.2·§5.1·§5.2·§8.2·§11.1·§11.2는 갱신했지만 §4.1·§2.1을 놓쳤다 — "이 결정을 언급하는
  절이 몇 개인지"를 사전에 전수 조사하지 않고 기억에 의존해 갱신한 게 원인이다.
- **Plan §2.3 인자 설계 단계에서 "이 MCP 서버가 여러 프로젝트를 다룰 수 있다"는 사실
  자체를 놓쳤다.** `project_list`가 워크스페이스·프로젝트 목록을 반환하는 툴이라는 걸
  알고 있었는데도, 인자 설계 시점에 "얼마나 많은 프로젝트가 실재하는가"를 실측하지
  않고 설계했다.

### 6.3 다음에 시도할 것 (Try)
