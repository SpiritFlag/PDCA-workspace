## 1. 개요

### 1.1 목적

MCP 서버에 prompts 표면을 열고, 형이 반복 지시해 온 워크플로 2종을 프롬프트로 등록한다.

- **job 1 `backlog_sync`** — 사이클 종료 후 백로그를 최신 상태로 되돌리는 절차
- **job 2 `make_cc_prompt`** — 백로그 항목을 CC용 Plan 작성 지시서로 바꾸는 절차

지침 원문의 확정본은 **부록 A**에 수록한다. 구현은 그 텍스트를 코드로 옮기는 일이다.

### 1.2 배경

- **6차(expand-mcp-agency, `v0.1.5`)** 가 `STATUS_MEANING`을 만들어 "완료/해소의 의미"를
  코드 한 곳에 박고 툴 description·UI 툴팁이 공유하게 했다(D-45). 의미는 단일 원천이 됐지만
  **그 의미를 언제 어떤 순서로 적용하는지(절차)** 는 여전히 형의 채팅 지시에만 있다.
- 실제로 이 지침들은 웹 대화에서 **백로그 갱신 5회 + CC 프롬프트 3회** 반복되며 형태가
  다듬어진 것이다(백로그 `8c486c18` detail). 형태가 안정됐는데 저장 장소가 없다.
- **MCP 스펙은 prompts를 "user-controlled" 표면으로 정의**하고 슬래시 커맨드를 대표
  인터랙션으로 예시한다(§3.1 M-4). 즉 "사람이 골라서 시작하는 절차"가 정확히 이 표면의 용도다.
- 6차 D-46이 cycles **쓰기** 툴을 미등록으로 남긴 것과 충돌하지 않는다 — prompts는 권한이
  아니라 지시문이다.

## 3. 요구사항

### 3.1 필수 실측 결과 (확정 사실 — 추정 없음)

> 형이 지정한 실측 4항목 + 설계에 직접 영향을 준 4건. 전부 코드·SDK 소스·공식 문서 직접 확인.

#### ★M-1. 현행 MCP 서버 구현의 구조

**파일 2개뿐이다.** [server/mcp/index.ts](../../../../server/mcp/index.ts)(37줄) ·
[server/mcp/tools.ts](../../../../server/mcp/tools.ts)(247줄).

```
POST /api/mcp
 └ authMiddleware (app.ts:39)          ← HTTP 레벨. JSON-RPC 메서드와 무관하게 전부 통과 필수
   └ mcpRoute.post('/')                 ← Origin 검증 (index.ts:12-16)
     ├ new McpServer({name:'pdca-workspace', version:'1.0.0'})
     ├ registerTools(server, ownerId)   ← ★ prompts 등록도 여기 옆
     ├ new StreamableHTTPTransport({sessionIdGenerator: undefined, enableJsonResponse: true})
     ├ await server.connect(transport)  ← ★ 이 이후에는 capability 등록 불가 (M-2)
     └ transport.handleRequest(c) → finally server.close()
```

- **요청마다 서버 인스턴스를 새로 만든다**(stateless). 프롬프트 등록도 요청마다 반복되지만
  텍스트 상수 등록이라 비용은 툴 10개 등록과 같은 수준이다.
- `registerTools(server, ownerId)`는 `ownerId`를 클로저로 받는다. **프롬프트는 DB를 읽지
  않으므로 `ownerId`가 필요 없다** — `registerPrompts(server)` 시그니처로 충분하다.

#### ★M-2. SDK가 prompts를 지원하는가 — **지원한다**

`@modelcontextprotocol/sdk` **1.30.0**(`node_modules` 실측). 확인 지점 4개:

| 항목 | 실측 | 위치 |
|------|------|------|
| 등록 API | `registerPrompt(name, {title?, description?, argsSchema?}, cb)` — `registerTool`과 동형 | `server/mcp.d.ts:181-185` |
| **capability 자동 선언** | `registerPrompt` → `setPromptRequestHandlers()` → `registerCapabilities({prompts:{listChanged:true}})`. **수동 선언 불필요** | `server/mcp.js:727-736`, `:397-406` |
| 핸들러 | `prompts/list`·`prompts/get` 핸들러를 SDK가 자동 등록. 인자 검증(`safeParseAsync`)도 SDK가 하고 실패 시 `McpError(InvalidParams)` = `-32602` | `server/mcp.js:407-443` |
| 인자 메타 파생 | `promptArgumentsFromSchema` — zod 필드의 `.describe()`를 `description`으로, `.optional()` 여부를 `required`로 자동 변환 | `server/mcp.js:873-888` |

**→ 우회 비용 0. 툴 등록과 같은 패턴으로 쓸 수 있다.**

> ⚠️ **단, 등록 시점 제약이 있다.** `registerCapabilities`는 `if (this.transport) throw`다
> (`server/index.js:86-89`) — **`server.connect(transport)` 이후에 첫 `registerPrompt`를
> 부르면 런타임 예외.** 현행 코드가 `registerTools` → `connect` 순서라 그 옆에 넣으면
> 안전하지만, 이 순서 의존은 Design에 명시해야 한다(RK-57).

#### ★M-3. 인자 스키마 정의 방식과 값 타입 제약

- `argsSchema`는 zod raw shape(`{키: zodSchema}`)이다 — 툴의 `inputSchema`와 같은 형태.
- **그러나 값은 문자열만 온다**: 스펙의 `GetPromptRequestParamsSchema.arguments`가
  `z.record(z.string(), z.string()).optional()`
  (`node_modules/.../dist/esm/types.js:995-1004`). **`z.number()`·`z.array()`·`z.enum()`은
  클라이언트가 보낼 수 없다** — 전부 `z.string()` 계열이어야 한다.
- `.optional()`을 붙이면 `prompts/list` 응답의 `arguments[].required`가 `false`가 되고,
  누락돼도 `-32602`가 나지 않는다.

#### ★M-4. MCP 스펙의 prompts 정의 (2025-06-18)

- **"Prompts are designed to be user-controlled"** — 사용자가 명시적으로 골라 실행하는 표면.
  스펙이 직접 **슬래시 커맨드**를 대표 인터랙션으로 예시한다.
- `prompts/get` 응답은 `{description?, messages: [{role:'user'|'assistant', content:{type:'text', text}}]}`.
  **지침은 `role:'user'` 텍스트 1건**이면 충분하다.
- 에러 규약: 없는 프롬프트명·필수 인자 누락 = `-32602`, 내부 오류 = `-32603`.
- capability는 초기화 시 `{"prompts":{"listChanged":true}}` 선언 **MUST** — M-2대로 SDK가 처리.

#### ★M-5. 클라이언트 지원 — Claude Code는 **지원 확정**, claude.ai 웹은 **미확인**

| 클라이언트 | 지원 | 근거 |

| **Claude Code** | ✅ **문서 명시** | 공식 문서 "Use MCP prompts as commands": `/` 입력 시 **`/mcp__servername__promptname`** 형식으로 노출. 인자는 **공백 구분 위치인자**(`/mcp__github__pr_review 456`). #### M-6. l1-harness의 prompts 재사용 가능성 — **재사용 가능 (6T-1 채점 근거)**

[server/l1-harness.ts:73-81](../../../../server/l1-harness.ts)의 `rpc`:

```ts
export async function rpc(token: string | null, method: string, params?: unknown)
```

- **method가 문자열 파라미터**라 `rpc(t,'prompts/list')`·`rpc(t,'prompts/get',{name,arguments})`가

- 픽스처 불요: 프롬프트는 DB를 읽지 않아 `seedWorkspaceProject` 없이 `mintToken` 하나면 된다.
- ⚠️ **테스트 파일 배치**: `vitest.l1.config.ts`의 `fileParallelism: false`(6차 module-1에서
  실 DB 경합 때문에 도입)가 이미 있으므로 `.l1.ts` 파일이 3개가 돼도 안전하다 — **다만 신설
  파일 vs `mcp.l1.ts`에 추가 중 어디에 둘지는 Design 결정**(§7.2).

#### M-7. 인증·Origin이 prompts 요청에도 적용되는가 — **적용된다 (구조적)**

- [server/app.ts:39](../../../../server/app.ts)의 `.use('/mcp', authMiddleware)`는 **경로 단위**다.
  JSON-RPC 메서드는 body 안에 있으므로 미들웨어는 그것을 보지 않는다 → `prompts/*`도 **동일하게 401**.
- Origin 검증도 [server/mcp/index.ts:12-16](../../../../server/mcp/index.ts)의 **POST 핸들러 최상단**이라
  JSON-RPC 디스패치 이전에 실행된다 → `prompts/*`도 **동일하게 403**.
- `?token=` 쿼리파라미터 폴백(PAT 한정, D-18)도 같은 미들웨어라 그대로 적용된다.
- **→ 서버 측 추가 방어 코드 0줄.** C47은 "새로 만들 것"이 아니라 "구조가 이미 보장함을
  하네스로 못 박는 것"이다.

#### M-8. 지침이 참조할 단일 원천의 현재 위치

| 원천 | 위치 | 프롬프트가 참조하는 방법 |

### A-1. `backlog_sync` — 사이클 종료 후 백로그 최신화

> **description(안)**: "사이클을 닫은 직후 백로그를 최신 상태로 되돌릴 때. 종료 상태 갈라 찍기 ·
> 이월 항목 생성 · 낡은 항목 재평가를 한 번에 처리한다"
> **인자**: `projectName`(선택) — 대상 프로젝트명 · `cycleName`(선택) — 대상 사이클 폴더명.
> 예: `expand-mcp-prompts`

```text
방금 닫힌 PDCA 사이클을 기준으로 백로그를 최신 상태로 되돌린다. 아래 순서를 그대로 따른다.

0. 프로젝트 확정
   - project_list로 워크스페이스·프로젝트 후보를 확보한다.
   - projectName이 주어졌으면 그 이름과 대조해 한 프로젝트로 좁힌다. 이름이 여러 건과
     매칭되면(같은 이름이 다른 워크스페이스에 있는 경우 등) 되묻는다.
   - 비었으면 후보 전체를 나열해 형이 고르게 한다. 하나뿐이어도 임의로 확정하지 않고
     "이 프로젝트가 맞나?"로 확인받는다 — 워크스페이스가 늘어날 수 있어 지금 하나인 것이
     계속 하나라는 보장이 없다.

1. 사이클 확정
   - cycleName이 주어졌으면 그 사이클을 대상으로 한다.
   - 비었으면 그 프로젝트의 cycle_list로 버전 목록을 받아 가장 높은 버전의 name을 후보로
     삼고, "이번 대상은 <사이클명>이 맞나?"를 한 줄로 확인받은 뒤 진행한다. 추측으로
     진행하지 않는다.

2. 근거 읽기
   - document_list로 경로를 확인하고 document_read로 그 사이클의 report를 읽는다.
     판정이 갈리는 항목이 있으면 analysis도 읽는다.
   - backlog_list를 상태 필터 없이(전 상태) 호출해 전건을 확보한다.
     열린 항목만 보면 이미 닫힌 항목과의 중복 생성을 놓친다.

3. 종료 상태 갈라 찍기
   - 이 사이클이 겨냥해서 해결한 항목 → done
   - 의도한 건 아닌데 다른 작업에 딸려 해결됐거나 필요 자체가 없어진 항목 → resolved
   - 두 상태의 정의는 이 서버 backlog_update 툴의 description에 적힌 것을 그대로 따른다.
     여기서 다시 정의하지 않는다.
   - closedOn은 사이클 완료일(YYYY-MM-DD).
   - todo로 되돌리는 전환은 사람 전용이므로 요청하지 않는다.

4. detail 갱신 — 원안 보존
   - 상태를 바꾸거나 범위를 줄일 때 detail 맨 앞에 한 줄 블록을 덧붙인다.
       [YYYY-MM-DD 완료|해소|축소|갱신 — 근거: <사이클명> <SC/FR/§ 번호>]
   - 기존 본문은 지우지 않는다. 원안이 뒤로 밀리면 "(원안)" 접두를 붙여 아래에 남긴다.

5. 신규 항목 생성
   - report의 이월·신규 제안(등급별 이월 · 회고 Try · 다음 사이클 후보)을 각각 항목으로 만든다.
   - 만들기 전에 2단계에서 확보한 전건과 제목·detail을 대조해 이미 있는 항목인지 먼저 확인한다.
     있으면 새로 만들지 말고 그 항목의 detail을 갱신한다.
   - detail에 출처를 반드시 남긴다: (<사이클명> report §<번호>)
   - openedOn은 사이클 완료일. 상태는 항상 todo에서 시작한다.

6. 전제가 바뀐 기존 항목 재평가
   - 이번 사이클로 근거나 범위가 달라진 항목은 상태를 바꾸지 말고 4단계 형식으로
     [… 축소] 또는 [… 갱신]만 기록한다.

7. 판단 보류
   - done인지 resolved인지 갈리는 항목, 여러 건이 묶여 통째로 닫을 수 없는 항목,
     폐기 여부가 사람 결정인 항목은 바꾸지 말고 질문으로 남긴다.

8. 보고
   - 대상 프로젝트·사이클명을 한 줄로 밝힌다.
   - 처리 요약 표를 낸다: done / resolved / 신규 / 갱신 각 구획에 항목 제목 한 줄씩.
   - 이어서 보드 집계(상태별 건수)를 낸다.
   - 7단계의 질문이 있으면 표 아래에 번호를 매겨 따로 낸다.
```

### A-2. `make_cc_prompt` — 백로그 항목 → CC용 Plan 작성 지시서

> **description(안)**: "백로그 항목을 Claude Code가 그대로 실행할 수 있는 Plan 작성 지시서로

> `cycleName`(선택)

```text
백로그 항목을 Claude Code가 바로 실행할 수 있는 "Plan 작성 지시서"로 바꾼다.
결과물은 지시서 텍스트 한 덩어리이며, 이 대화에서 설계나 구현을 시작하지 않는다.

0. 프로젝트 확정
   - project_list로 워크스페이스·프로젝트 후보를 확보한다.
   - projectName이 주어졌으면 그 이름과 대조해 한 프로젝트로 좁힌다. 여러 건과 매칭되면 되묻는다.

1. 대상 확정
   - targets가 주어졌으면 그것으로 항목을 특정한다(쉼표 구분, 항목 id 또는 제목 일부).

   - 비었으면 그 프로젝트의 backlog_list로 열린 항목을 훑고 우선순위·의존 관계를 근거로
     후보를 2~3건 제시해 형이 고르게 한다. 임의로 정하지 않는다.
   - cycleName이 주어졌으면 그 이름을 쓰고, 비었으면 4번 규칙으로 만들어 제안한다.

2. 근거 확보
   - 대상 항목의 detail을 끝까지 읽는다. detail이 가리키는 문서(report §번호 등)가 있으면
     document_read로 원문까지 확인한다.
   - 백로그 detail의 요약만으로 지시서를 쓰지 않는다.

   1) 산출물 — docs/PDCA/<연월>/<사이클명>/<사이클명>.plan.md 한 개만.
      착수 전 `git log -1 -- docs/RULE.md`로 RULE.md 최신 확인 지시.

      선행 사이클과의 관계(무엇의 후속인가)가 있으면 함께 적는다.
   3) 스코프 N건 고정 — 항목을 번호로 세고 "확장 금지"를 명시한다.
   4) 명시적 Out of Scope — 인접해서 손대고 싶어질 것들을 미리 열거하고,
      작업 중 발견하면 고치지 말고 백로그로 재이월하라고 지시한다.
   5) 착수 전 실측 표 — 추정 금지. 관련 파일·함수·스키마를 직접 읽어 확정 사실로 적게 한다.
      성패를 가르는 항목에는 ★를 붙이고, 지원 여부가 불확실한 것은
      "지원하지 않으면 우회 비용을 산정해 보고"까지 지시한다.
```
